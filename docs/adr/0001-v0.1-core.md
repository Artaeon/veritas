# ADR 0001: Veritas V0.1 Core

- Status: Accepted
- Date: 2026-08-23

## Context

Veritas compiles untrusted, declarative knowledge into a typed intermediate
representation and evaluates it deterministically. V0.1 must prove that the
syntax, compiler, runtime, and proof model can remain separate while supporting
useful inference. It must not contain domain-specific concepts.

## Decision

### Modules

The first release is one TypeScript package with cohesive modules rather than a
workspace of micro-packages:

- `parser`: source text to an untrusted syntax tree, with source locations.
- `compiler`: name resolution, type checking, validation, and AST-to-IR lowering.
- `model`: the syntax tree and immutable, typed runtime IR.
- `runtime`: monotonic forward chaining and query evaluation.
- `proof`: proof data is represented in the runtime model and formatted at the edge.
- `canonical`: stable serialization and SHA-256 bundle identity.
- `cli`: file I/O and presentation only; it contains no reasoning logic.

The dependency direction is `cli -> parser -> compiler -> runtime`. The runtime
accepts only compiled IR and never reads DSL syntax.

### Compiler pipeline

```text
UTF-8 source -> line lexer/parser -> AST -> symbol collection
             -> name/type validation -> typed IR -> canonical hash
```

Parsing and compilation accumulate diagnostics in source order. Any error makes
the bundle non-executable. Knowledge files never execute JavaScript, import
files, access the network, or cause filesystem effects.

### Fact model

An entity has exactly one declared nominal type. A ground fact is a typed cell:

```text
(entity, property) = value
```

Attributes contain primitive values. Predicates contain Boolean values. The
cell key is independent of its value, so contradictory Boolean assertions can
be detected. Initial and derived facts use the same representation but retain
different proof origins.

V0.1 primitives are `Boolean`, `Integer`, `Decimal`, `String`, `Symbol`, `Date`,
and `Duration`. Integer and Decimal literals are retained canonically as strings
in IR; comparisons use exact `BigInt` and normalized decimal arithmetic, never
IEEE-754. Date and Duration are parsed and carried but arithmetic is deferred.

### Truth semantics

Queries for Boolean predicates return `TRUE`, `FALSE`, `UNKNOWN`, or `CONFLICT`.
The runtime uses an open world:

- no asserted or derived value means `UNKNOWN`;
- `UNKNOWN` is never treated as `FALSE`;
- simultaneous support for `true` and `false` means `CONFLICT`;
- no rule receives implicit priority.

Attribute queries return a known value, `UNKNOWN`, or `CONFLICT` when distinct
values have support.

### Rule semantics

A rule declares one typed variable, one or more conjunctive conditions, and one
effect. For every entity of the variable type, conditions are evaluated from a
snapshot of known facts. A rule fires when every condition has concrete matching
support. Under paraconsistent evidence semantics, contrary support does not
erase a matching branch; the proof cites only matching support. This preserves
monotonicity when conflicts arise at different fixpoint depths.

Derived facts are added monotonically. Evaluation repeats in canonical entity
and rule order until no new `(cell, value)` support is added. The finite set of
entities, properties, rules, and literal effects guarantees termination for
V0.1, including cycles such as `A -> B` and `B -> A`.

### Query semantics

The CLI accepts a ground property reference such as `john.adult`. A query never
mutates runtime state. `query` returns the result and bundle identity;
`explain` additionally renders all proof roots for the result. Missing cells are
reported explicitly.

### Proof model

Every supported fact has one or more proof nodes:

- `asserted`: fact ID and source span;
- `derived`: rule ID, variable substitution, condition evaluations, and the proof
  references that supported those conditions.

Proof nodes form an acyclic graph because a derived node references only the
snapshot from the previous fixpoint step. Formatting sorts IDs and references,
making output byte-stable.

### Error handling

Diagnostics have a stable code, severity, message, file, line, column, and an
optional hint. The parser does not recover by silently discarding a malformed
declaration. Duplicate declarations, unknown names, invalid operators, and type
mismatches are compile errors. The CLI exits non-zero and does not invoke the
runtime when any error exists.

### Constraint backend boundary

The future solver boundary is an interface over typed constraints; V0.1's
comparison evaluator is its only implementation. No solver dependency is added
until the language needs one.

## Consequences

The first language is intentionally less natural than controlled English but is
unambiguous and easy to audit. It does not yet support relations, multiple rule
variables, negation-as-failure, imports, units, date arithmetic, or user-defined
functions. Adding them requires a new ADR and IR version.
